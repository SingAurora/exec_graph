# 项目详情页 UI 设计

本文记录项目详情页当前确定的网页端展示逻辑。它是产品设计文档，不描述代码结构，也不代表当前页面已经完全按此实现。

## 1. 页面定位

项目详情页用于阅读一个项目中持续发生的行动，以及这些行动如何连接成主线和支链。它不是任务清单，也不要求用户先设定目标再提交结果。

用户进入项目后，需要理解三件事：

```text
最近发生了哪些行动
这些行动如何连接成主线和支链
不同的人正在沿着哪些路线继续行动
```

页面采用类似 Git 工程历史的工作区：左侧查看节点关系，右侧阅读当前节点的行动记录。

```text
项目头部：项目名称、简介、参与人数、主线/支链上下文

┌────────────────┬────────────────────────────┐
│ 节点图          │ 当前节点详情                │
│                │                            │
│  ● 节点 #5       │ 节点 #5 · 主线              │
│  │             │ 整理出自己的番茄炒蛋原则      │
│  ● 节点 #4 ─┐    │ 作者、时间、行动记录、图片      │
│  │          ├─● 支链 A                         │
│  ● 节点 #3   └─● 支链 B                         │
│                │ 查看形成过程 · 沿此继续 · 另开方案 │
└────────────────┴────────────────────────────┘
```

页面的主要动作是“点击节点，查看节点详情”。用户不需要在左侧和右侧之间反复理解不同的信息层级。

## 2. 节点图

### 2.1 节点代表一次行动记录

每个节点只代表用户真实发生的一次行动记录。行动可以是尝试、复做、调整、失败、部分结果或新的观察，只要用户愿意记录，就可以成为节点。系统不要求行动对应某个目标，也不判断行动是否“完成”。

用户可以先行动，再与 AI 对话，把行动经过、结果和观察整理成一份记录，最后决定是否发布为节点。AI 对话是记录的形成过程，节点是公开可阅读的行动结果。

节点编号使用项目内稳定的 `节点 #N`：按节点创建顺序分配，节点进入主线或支链后都不重新编号，也不会因为主线排序变化而改变。主线/支链是节点的关系属性，编号是节点本身的身份。

节点图和节点详情可以同时显示路径位置，例如 `节点 #12 · 主线第 5 个`、`节点 #18 · 支链 A 第 2 个`。路径位置帮助用户理解当前节点在某条路径中的顺序，稳定编号用于唯一引用节点。

### 2.2 主线和支链

- 主线使用一条连续、较粗、颜色明确的竖线。
- 支链从产生分叉的节点旁边引出，使用较细的线和较弱的颜色。
- 主线节点保持连续可读，较长或不活跃的支链默认折叠到分叉附近。
- 活跃支链显示名称、参与者和最近行动时间；不把支链描述成待完成的方案。
- 主线由后续行动、接续关系、认可反馈和近期活跃度等事实逐步形成。算法只决定展示顺序和视觉强调，不改变节点原始编号。
- 主线和支链表达行动之间的关系：主线是项目当前被更多人接续的表达，支链是从某个节点分出去的另一条行动路线。

例如：

```text
节点 #8：记录第一次番茄炒蛋
 ├── 节点 #9：尝试提前起锅
 ├── 节点 #10：改变番茄处理顺序
 └── 节点 #11：在更短时间内复做
```

这里的三个支链节点都是独立行动记录，不是预先登记的三条方案。

### 2.3 节点摘要

节点摘要只帮助用户定位，不承担完整阅读任务。每个节点可以显示：

- 节点编号，以及可选的主线/支链路径位置。
- 主线或支链标识。
- 行动记录标题或首句。
- 作者头像和用户名。
- 行动发生或发布的时间。
- 是否存在图片，以及最多 3 张图片缩略图。

默认选中最新主线节点。用户从右侧打开某个支链节点后，左侧自动切换到包含该节点的支链路径，并高亮该支链与它的分叉位置。

### 2.4 节点操作

- 点击节点：右侧切换到该节点。
- 点击支链节点：进入该支链的节点路径，右侧显示该行动记录。
- 点击“回到主线”：恢复主线节点路径。
- 点击“回到最新”：选中最新主线节点。
- 点击“沿此继续”：以当前节点为上下文，开始记录下一次行动。
- 点击“另开方案”：从当前节点建立一条新的支链，然后记录行动。
- 节点图支持按节点编号定位，长链历史不在左侧一次性展开所有支链。

## 3. 右侧节点详情

右侧只展示当前选中节点的一条完整行动记录。它不使用“摘要 / 详情”切换，因为摘要和详情不是两个业务状态，而是同一条记录的不同呈现层级。默认直接展示足够阅读的行动内容，需要追溯时再进入形成过程。

### 3.1 节点头部

```text
节点 #4 · 主线
整理出自己的番茄炒蛋原则
jo · 10/11 20:05 · 2 条后续行动 · 2 条支链
```

头部说明节点编号、主线/支链位置、行动记录标题、作者、时间和后续关系。不额外生成一个需要别人总结的标题。

### 3.2 默认内容

其他用户默认看到行动记录：

```text
头像  用户名  时间

这次把番茄先炒到出汁，再加入蛋液。两次复做都控制在 20 分钟内，第二次减少了调味步骤，出锅后更接近想要的酸甜味。

图片缩略图

留下的观察：火候变化比调味先后更影响口感。

查看形成过程   查看 AI 对话   沿此继续   另开方案
```

公开内容默认由行动经过、实际结果和行动者留下的观察组成。节点可以没有图片，也可以包含多张图片；图片只在实际存在时显示。

“查看形成过程”进入独立资料页，展示这条记录从原始行动描述到公开 Markdown 的整理过程；“查看 AI 对话”展示形成这条记录的连续对话历史。两者都属于同一条行动记录的上下文，不再拆成彼此独立的内容。

### 3.3 一个节点中的内容

一个节点对应一条行动记录，不再把多条行动强行合并，也不再把一次行动拆成两种内容。记录可以包括：

- 行动标题或首句。
- 行动者、时间和可选地点等基本信息。
- 实际做了什么，以及过程中的关键变化。
- 行动产生的结果、失败或部分结果。
- 行动者留下的观察、判断或下一步想法。
- 图片等行动证据。
- 用于形成记录的 AI 对话和 Markdown 历史。

如果用户连续做了两次行动，应发布为两个节点；后一个节点通过接续关系连接前一个节点。这样每个节点都保持清楚的时间和行动边界，也让主线和支链能够反映真实的行动路线。

## 4. 滚动与阅读

页面采用固定职责的双栏工作区：

- 左侧只浏览节点关系。
- 右侧只浏览当前节点的行动记录。
- 项目头部属于工作区上下文，不随着某个节点内容重复出现。
- 节点图和详情区各自只有一个滚动区域，不再叠加页面、卡片和列表的多层滚动。
- 右侧滚动较深时，当前节点仍保持选中状态。
- 右侧内容切换后，滚动位置回到该节点详情顶部。

这种滚动方式是 Git 历史浏览器式的明确双栏，而不是把多个内容流临时拼在一起。

## 5. 用户阅读路径

默认路径是：

```text
打开项目
→ 自动选中最新主线节点
→ 阅读这次行动做了什么、产生了什么结果
→ 看左侧主线最近几个节点，理解项目正在形成的表达
→ 发现某个节点有支链
→ 点击支链节点，比较不同的实际行动路线
→ 需要追溯时查看记录形成过程或 AI 对话
→ 沿当前节点继续记录，或从这里另开一条支链
```

用户先看到最近发生的行动，再决定是否追溯上下文或加入其中一条行动路线。

## 6. 暂时不用的帖子简略信息规范

这套规范已经确定，但当前项目详情页以节点图和右侧行动详情为主，暂时不启用完整的帖子简略卡。它保留给项目列表、发现页、历史列表或未来的节点摘要入口。

### 6.1 简略卡内容

```text
节点编号 · 主线/支链
行动记录标题
头像 用户名 · 时间
行动摘要
图片缩略图
```

### 6.2 显示限制

- 标题最多 1 行，超出省略。
- 作者信息 1 行，头像与用户名同时显示。
- 行动摘要最多 3 行，超出省略。
- 图片最多显示 3 张缩略图。
- 没有图片时不保留图片区域。
- 默认显示行动摘要，不显示目标字段或状态提示。
- 简略卡不展示 AI 对话正文，只提供进入记录形成页的入口。

### 6.3 简略卡的使用原则

简略卡的任务是让用户判断“这条行动记录值不值得点开”，不是替代完整记录。它必须保持稳定高度、信息层级清楚，并避免把行动标题重复显示为额外的节点标题。

## 7. 当前设计结论

项目详情页采用 Git 工程历史式布局：左侧节点图表达行动的主线、支链和接续关系，右侧显示选中节点的一条完整行动记录。项目不要求预先设定目标，也不提供额外状态字段；每个节点只记录一次真实行动。AI 对话和 Markdown 是这条记录的形成过程，通过按钮进入独立资料页查看。帖子简略信息作为后续列表和发现页的复用规范保留，暂时不作为项目详情页的主要内容。
