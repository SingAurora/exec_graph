# 番茄炒蛋示例的观察场景

这个示例用于检验行动记录、表达、引用和约定的展示是否容易理解。它是静态演示，不代表真实用户实验，也不把主线演示算法的选择解释为厨艺排名。

## 数据边界

- 保留项目内 14 个节点、15 条引用，以及原有主线和分支结构。
- 每个节点只记录当次行动。一顿里留半盘静置属于同次行动，不把几天的复做打包成一个节点。
- 每个人只报告自己实际做过、尝过的结果；引用他人记录时说明出处，不假装吃过对方那盘。
- 时间有统一的比较范围：开始洗菜到装盘，不含煮饭、洗锅。没有计时就明确没有计时；两人协作不当成单人速度。
- 观点来自当前行动和引用祖先；较早发布的其他分支也不能自动成为事实背景。
- 食材图片标明示意图，不作为这次虚构晚餐的实拍证据。移除原来的无关沙拉图片。
- 不给每个节点强行添加约定。已经发布的跨作者例外有来源作者同意，不制造未经同意却已发布的例外来凑状态。

## 建议阅读路径

1. 打开默认的 #13，看记录是否足以知道这顿饭做了什么，切换表达后是否能看出不同内容。记录较长，应能正常滚动。
2. 沿主线回看 #10、#9、#8、#5、#2、#1：鸡蛋发硬的问题如何逐渐形成“看状态、分别处理食材”的判断，中间是否也容得下失败。
3. 切到 #14，再看 #11 和 #7：来源不同、偏好不同，能否看出为什么多汁版本值得保留，而不是自动归为做得不如主线。
4. 点击 #10 → #13 和 #3 → #6：一个是自己同意例外，一个是来源作者同意例外；核对原因与两端记录是否一致。
5. 点击 #4 → #7：普通符合约定的跨作者引用，不出现 ×。
6. 查看 #12：失败记录能否独立成立，不需要补一段成功结论或行动目标。
7. 在 #13 或 #6 查看形成过程：对话能否解释事实如何补齐、观点是谁表达的，而不是直接把成文原样当用户的开场输入。

## 一致性验证

`frontend` 的 `bun run test:graph` 同时检查图语义与示例来源：引用来源存在且早于当前发布、上下文计数完整去重、约定核对只指向直接来源、批准者是来源作者、文档和对话中的节点引用没有越出当前引用历史。
