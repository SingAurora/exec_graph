# 执行图谱前端重设计方案

> 本文是界面与交互的改版基线，不替代 [产品逻辑设计](./product-logic-design.md) 和 [执行力逻辑递进](./execution-force-logic.md)。前两者解释产品为什么成立；本文定义用户如何看懂、使用并持续回到它。

> **状态说明（2026-09-21）**：本文同时保留改版原则和历史实施计划。第 6 节描述目标交互，第 9 节的优先级已按当前实现重新标注；已完成内容不应继续视为待开发事项。当前真实实现以 [当前系统基线](./current-system-baseline.md) 为准。

## 1. 改版目的

### 1.1 具体对象、用户与单一任务

- **产品对象**：执行图谱（Exec Graph），一个把真实行动、证据、AI 验证和阶段记录组织为可接续路径的执行系统。
- **首要用户**：正在推进复杂个人项目的人。他们会遗漏、分叉、补足、回收，却不想把真实工作压扁成一串待办事项。
- **界面的单一任务**：用户每次打开网站，都能立刻判断**现在最值得处理的一个行动节点**，并在处理后留下可信、可接续的记录。

因此，界面不能让人觉得在操作普通任务管理器。它不应以“任务数量、完成率、日程、团队协作”为主叙事；它应让人看见：

```text
我做了什么行动
-> 系统如何验证
-> 哪些内容已经成为记录
-> 接下来从哪里推进
```

### 1.2 本次改版要解决的问题

当前页面已有必要功能，但信息被拆散在卡片、说明文字和多个配置入口里。用户进入后常会遇到以下判断成本：

1. 不知道第一件该做什么，也难以区分“待推进”“正在审查”“等待确认”。
2. 项目页同时承担工作台、历史记录、图谱、配置，主次不够鲜明。
3. 节点、完成记录、AI 审查的关系需要读大量文字才能理解。
4. 节点图有价值，但不应抢占日常推进的主界面。
5. 智能合约、审查 AI、个人密钥这些系统配置不该与行动操作争夺注意力。
6. 当前暖纸张网格和展示性标题较强，容易读成“笔记/任务应用”，没有形成“可信行动档案”的独特识别。

### 1.3 非目标

本轮不以以下方向为目标：

- 不做传统日历待办、番茄钟、习惯打卡或工时统计；工作总览可以按月展示已经发生的行动，并允许 AI 基于当天记录生成日结分析。
- 不用进度百分比代替行动记录与现实反馈。
- 不让关系图成为所有页面的背景装饰。
- 不为每个概念附一整段产品说明；信息结构本身应说明大部分用法。
- 不把公共探索、关注、推荐等社交功能提前塞进个人推进主流程。

### 1.4 视觉成果目标

美观不是为页面增加装饰，而是让产品的事实、责任与推进关系被一眼读懂。执行图谱应该显得**冷静、可信、正在推进**，而不是像待办堆积、社交信息流或营销页面。

#### 用户感受

```text
5 秒：看出当前最需要处理的行动，以及它处于验证的哪一环。
30 秒：区分可推进、等待确认、正在审查和已锁定记录。
一次使用后：记住这里以行动证据和锁定记录组织工作，而不是勾选任务。
```

#### 视觉记忆点

产品必须由以下三件事共同形成辨识度：

```text
终端提示式 >_ 标识：代表开始一项可执行的行动。
验证轨：代表行动经过审查并进入记录的过程。
阶段记录账本：代表已锁定成果的连续历史。
```

即使不显示 Logo，工作总览、节点详情和记录页的截图也应因验证轨、结构化证据与账本式记录而被识别为执行图谱，而不是通用项目管理工具。

#### 美观验收标准

- 一个首屏只有一个主视觉重心和一个明确的主操作；其他信息通过层级而非更大的字或更多颜色争夺注意力。
- 颜色只表达状态与操作语义，禁止用状态色填满背景或做无意义装饰。
- 不嵌套卡片；页面分区使用边界、留白和连续列表，重复对象才使用克制的单层卡片。
- 标题、正文、Mono 元数据的层级稳定。长标题、长合约名和长模型名必须换行或截断，不能挤压相邻内容。
- 节点详情应像一份可审阅材料，记录页应像一组连续档案，不能退化成同一套卡片模板。
- 项目关系图与执行网络必须有可阅读的图谱结构、图例和聚焦对象；关系清单只能是补充阅读模式。
- 动效只服务状态变化、浮层进入和可点击反馈；静止状态必须足够清楚。

## 2. 产品界面模型

产品的四个词不应只是 Logo 旁边的文案，而应成为所有页面的共同语法。

| 结构词 | 用户视角 | 界面对象 | 主要入口 |
| --- | --- | --- | --- |
| 行为 | 我实际做了什么 | 推进节点、补充节点、收束行动 | 节点工作区 |
| 验证 | 这次行动是否站得住 | 冻结的任务标准、证据、AI 审查、用户确认 | 节点详情 |
| 记录 | 哪些行动已成为不可随意改变的事实 | 阶段完成记录、事件日志 | 项目记录、公共项目 |
| 推进 | 下一步从哪里继续，是否需要拆分或收束 | 当前节点、路径、来源关系 | 工作总览、项目工作台 |

这四层必须在同一项目内有清楚的视觉区别：

- 行为是可编辑、可继续的当前对象。
- 验证是附着在行为上的判定过程，而不是另一条任务。
- 记录是已锁定的历史对象，应稳定、可引用、默认只读。
- 推进是从当前节点引出的行动选择，而不是一条泛化的“下一步”提示。

## 3. 设计方向

### 3.1 方向：行动档案室，而不是任务看板

界面应有一种克制的“行动档案室”感：每次推进是一份事实材料；AI 审查是一份可追溯的判定；锁定后形成一条稳定的记录。它不是模拟区块链视觉，也不使用链条、六边形或密码学装饰。

这个方向的材料来源是产品真实对象：任务书、证据条目、审查结论、事件时间线、被锁定的阶段记录。视觉重心放在层级、边界、状态与顺序，而不是大面积装饰。

### 3.2 唯一的标志性元素：验证轨

每一个重要节点、审查结论和阶段记录都使用一条统一的**验证轨**表达其位置和状态：

```text
行为节点  o---------o  AI 审查  o---------o  用户锁定
           可推进              待确认              记录
```

- 在工作总览中，它是每条待处理项左侧的细竖轨，快速表达当前卡在什么环节。
- 在节点详情中，它是顶端的横向步骤轨，显示当前环节和已发生的审查事件。
- 在项目记录中，它是竖向事件轨，连接完成记录与被覆盖节点。
- 在关系图中，它退化为边与节点状态，不再额外重复说明。

验证轨是产品的视觉签名，因为它直接表达“行动不是天然完成，记录来自验证后的锁定”。除它之外，其他元素保持安静，避免多个视觉噱头互相竞争。

### 3.3 写作与命名原则

- 用用户能做的动作命名：`提交推进结果`、`确认并锁定`、`新增补足节点`、`查看审查结论`。
- 同一动作在整个流程中保持同一名称。按钮写“确认并锁定”，成功反馈写“已确认并锁定”。
- 页面标题描述用户所在的位置：`工作总览`、`项目记录`、`节点详情`，不用系统内部术语。
- 只在无法从结构推断时补一行帮助文字。错误与空状态必须指出下一步。
- “智能合约”是项目级规则对象；“AI 审查”是某次节点的执行结果，不混用。

### 3.4 审查澄清：复审材料，不是自由对话

AI 审查可能误读证据，但这不能成为改写冻结任务、原始完成说明或原始证据的入口。节点详情在已有 AI 结论后提供 `补充审查说明`，其表单必须先区分两种情况：

- `只澄清已有证据`：选择被误解的验收标准，说明误解所在，并定位原始材料中的证据位置。系统保留前一轮结论，以冻结规则、原始提交、前一轮结论和澄清材料发起新的审查轮次。
- `我完成了新的工作`：不允许提交到澄清复审；用户应创建补足推进节点，让新增工作成为新的行动证据。

每一轮都必须记录审查配置快照、用户澄清、AI 结论和逐条验收结果。事件页提供“复制全部审查内容”，导出冻结目标、原始提交、全部审查轮次及事件记录，方便对外讨论或留档。

## 4. 视觉系统

### 4.1 设计令牌

采用低压力、正规管理系统的视觉基底：中性冷灰承载大面积页面，蓝色表示默认操作，状态色只承担语义。产品的独特性来自验证轨、节点关系和锁定记录，而不是高对比或压迫性的视觉语言。

| 令牌 | 色值 | 用途 |
| --- | --- | --- |
| `canvas` | `#F7F8FA` | 全局画布，中性冷灰 |
| `surface` | `#FFFFFF` | 正文、表格、弹窗、输入区域 |
| `sidebar` | `#F2F4F7` | 左侧项目区与次级导航 |
| `ink` | `#1D2939` | 标题、主要文本、关键边界 |
| `muted` | `#667085` | 次级文本、说明、非关键元数据 |
| `rail` | `#E4E7EC` | 分隔线、验证轨、未激活关系 |
| `action` | `#1677FF` | 默认操作、链接、当前选中项 |
| `review` | `#D97706` | AI 审核中、需要留意 |
| `locked` | `#2E8B57` | 已锁定记录、审查通过 |
| `gap` | `#D14343` | 未满足、需补足、不可执行错误 |

蓝色是唯一的默认行动色：新建、提交、保存、链接和当前选中项使用蓝色或浅蓝底。绿色不再承担普通链接或装饰，只表示已通过或已锁定；黄、红只在需要处理的审查或风险上出现。避免用不同浅色背景堆砌卡片，也避免装饰性渐变。

#### 主题实现约束

- `frontend/src/styles.css` 中的 CSS 自定义属性是配色的唯一来源；亮色定义在 `:root`，暗色定义在 `[data-theme='dark']`。
- 页面组件只使用 Tailwind 语义令牌，如 `bg-paper`、`bg-surface`、`text-ink`、`border-rail`、`bg-signal`，不直接填写基础色值。
- Cytoscape 关系图与 Logo 等无法使用 Tailwind 的部分，通过 `frontend/src/lib/theme.ts` 读取同一套令牌；主题切换后图谱必须重新绘制。
- 主题由根元素的 `data-theme` 控制，`applyTheme(mode)` 负责保存用户选择并通知需要重新计算颜色的组件。新增主题时只扩展令牌值，不改业务组件。

### 4.2 字体

保留两种明确角色：

- **标题、正文与表单**：`Inter`，用 600/700 区分页面标题和区块标题，保持管理系统的清晰与稳定。
- **事实/系统信息**：`IBM Plex Mono`，用于节点 ID、状态、日期、审查来源、关系标签、计数。

推荐字阶：

```text
页面标题      32px / 40px
区块标题      20px / 28px
行标题        15px / 22px
正文          14px / 22px
元数据        12px / 18px
Mono 标签     11px / 16px
```

不使用负字距。不随屏幕宽度缩放字号。紧凑区域以换行和稳定高度处理，而非压缩文字。

### 4.3 边界、圆角、阴影与动效

- 主体结构以 `1px rail` 分割；当前状态用左侧 2px 色条或验证轨强调。
- 卡片最大 `8px` 圆角；列表行、标签栏、输入框通常 `6px`。不使用大圆角胶囊作为主要界面语言。
- 阴影仅用于菜单、浮层、弹窗，且非常浅；正文页面靠边界和留白分层。
- 主要动效仅限：队列项悬浮时 120ms 背景变化；验证轨状态变化 180ms；弹窗 160ms 进入。所有动效遵循 `prefers-reduced-motion`。

## 5. 全局信息架构

### 桌面 Web 布局

借鉴 GitHub 的清楚责任边界，而不是复制其页面：顶栏负责跨域切换，左栏只保留用户最常反复进入的个人项目，主栏承载当前页面。

```text
+--------------------------------------------------------------------------------+
| >_ 执行图谱     工作总览   探索                 搜索      + 新建项目   头像  |
+---------------------------+----------------------------------------------------+
| 我的项目                  | 页面上下文 / 面包屑                 主要操作       |
| [项目 A]                  +----------------------------------------------------+
| [项目 B]                  |                                                    |
| [项目 C]                  |                    主内容                         |
|                            |                                                    |
| + 新建项目                |                                                    |
|                            |                                                    |
| 个人设置                  |                                                    |
+---------------------------+----------------------------------------------------+
```

规则：

1. 顶栏固定，包含跨项目能力：`工作总览`、`探索`、搜索、`新建项目`、用户菜单。
2. 左栏固定并可独立滚动，只显示“我的项目”、新建项目和个人入口；不塞智能合约、设置、关系图等全局功能。
3. 主内容顶部固定在主要滚动区的上方。返回应放在这一页的顶部上下文区，而非页面正文中。
4. 智能合约、项目资料、审查 AI 都是项目内的标签页；个人密钥、账号、合约库是用户菜单进入的设置页面。

## 6. 页面重构

### 6.1 工作总览：先处理，再浏览

工作总览是登录后的根路径，不是统计仪表板。它要在第一个屏幕内交代用户应该做什么。

```text
工作总览                                              + 新建项目
现在该处理什么

等待你的确认  2
| 验证轨 | 项目名 / 节点标题                    AI 未通过 · 处理结果 > |
| 验证轨 | 项目名 / 节点标题                    AI 已通过 · 确认锁定 > |

AI 审核中      1
| 验证轨 | 项目名 / 节点标题                    已提交证据              |

等待推进       3
| 验证轨 | 项目名 / 节点标题                    提交推进结果 >          |

我的项目                                              管理智能合约 >
项目行：项目名 · 当前路径数 · 最新记录 · 当前处理事项 >
```

设计要求：

- 顺序固定为：`等待你的确认`、`AI 审核中`、`等待推进`。这是决策优先级，不按纯状态字母排序。
- 不使用“进行中的项目”“完成记录总数”等大指标占据首屏；总量可放在次级行中。
- 每个队列项点击后直接进入节点的正确标签页，不经过中间页。
- 空队列直接收起或压缩为一行，不保留大面积空卡。
- 项目列表采用紧凑行或克制卡片。展示“当前该处理什么”，不展示无意义的签名数。

### 6.2 项目工作台：一个项目的一张行动桌

项目页默认打开“节点”标签。首屏只服务当前行动；历史、关系和配置通过标签切换获得完整空间。

```text
< 返回工作总览
项目 / 私人                                                    [归档项目]
番茄牛腩研究
一套可复现的家庭炖煮方案
完成记录 3   当前路径 2   未锁定节点 2

节点 | 记录 | 关系图 | 项目资料 | 智能合约 | 审查 AI
--------------------------------------------------------------------------
当前需要处理
| 验证轨 | 补足香料用量                      [提交推进结果]               |
|        | 来自：基础食谱 / 发现缺口         待推进                        |

其他当前路径
| 验证轨 | 验证火候与收汁                   AI 审核中                      |

最近锁定记录
| 锁定轨 | 食谱基础流程已锁定              覆盖 2 个节点  查看记录 >     |
```

设计要求：

- 只把“当前路径”放在工作台上；已完成节点不是待办，不与当前节点并排竞争。
- 多条路径并存时，按需要用户处理的状态分组，再显示来源关系；同一条路径只显示一个当前节点。
- 在项目标题下展示简短的当前合约名称与审查 AI 名称，但不显示长正文。点击分别进入标签页或浮层。
- `记录`独立为项目标签，不埋在节点页底部。它是产品可信度的核心内容。
- `关系图`独立为项目标签，不作为默认页面。它用于理解复杂路径而非日常操作。
- 项目资料、智能合约、审查 AI 属于设置型标签，放在标签栏右侧或溢出菜单中，在视觉上弱于“节点、记录、关系图”。

### 6.3 节点详情：任务和完成是两份材料

节点不是一张万能卡。它由独立的任务描述与任务完成材料组成，因此保留双标签，但让顶部先说明当前状态。

```text
< 返回「番茄牛腩研究」                         节点 N-014
补足香料用量

行为 ---- 验证 ---- 记录
当前：待推进

任务描述 | 任务完成 | 事件
--------------------------------------------------------------------------
任务描述
冻结目标
补齐基础食谱中所有调味料的精确用量。

验收标准
[ ] 每种调味料标注量与单位
[ ] 与已有步骤一致

创建审核                         [查看完整结论]
通过 · DeepSeek / deepseek-chat · 2026-09-08
```

`任务完成`标签页：

```text
任务完成
证据材料
[补充说明文本框]
[上传或粘贴材料]

覆盖范围
本次可申请锁定：当前节点
可选择关联：此前未锁定的补足节点

[提交 AI 审查]

审查结论（返回后出现）
逐条验收标准：满足 / 未满足 / 证据不足
审查模型与配置快照
[确认并锁定]  [以未通过结论锁定]  [新增补足节点]
```

`事件`标签页：

```text
09-08 09:20  任务创建审核已通过       DeepSeek / deepseek-chat
09-08 11:32  已提交完成证据           用户
09-08 11:33  完成审核返回：未通过     Claude / Sonnet
```

设计要求：

- 创建审查和完成审查是独立事件，分别显示所用 AI 配置快照，不能用一个笼统“AI 已审核”代替。
- 验收标准应是结构化清单。审查结论逐条对应，不把所有判断藏在一段长文本中。
- 允许用户在 AI 未通过时锁定，但最终记录要明显标记 `AI 未通过后锁定`，不伪装为通过。
- “新增补足节点”必须显示其来源节点与拟覆盖关系；不要把它做成孤立的新任务。
- 首个节点没有“完成上一任务”的负担：它的任务描述定义项目第一次推进的目标，创建审核只审查任务是否可验证。

### 6.4 项目记录：不可变事实的阅读面

项目记录不是“已完成任务列表”，而是阶段闭合的档案。用时间顺序与覆盖范围建立可信度。

```text
项目记录                                               筛选：全部 v

2026-09-08
| 锁定 | 基础食谱流程已锁定
|      | 覆盖：N-002 备料试验、N-003 炖煮步骤
|      | AI 通过后由用户确认 · 查看审查 >

2026-09-06
| 锁定 | 食材选择完成
|      | 覆盖：N-001 首次推进
|      | AI 未通过后锁定 · 查看原因 >
```

设计要求：

- 每条记录明确呈现覆盖哪些节点、AI 结论、用户最终决定、所用合约与 AI 配置版本。
- 记录详情默认只读，允许引用、分享和查看源节点，但不允许原地修改内容。
- 用筛选而不是大量信息说明：`全部`、`AI 通过锁定`、`AI 未通过后锁定`、`覆盖多节点`。

### 6.5 关系图：理解路径，而不是制造复杂性

关系图只在项目内存在，默认从上到下表达时间与接续关系。它必须附带图例和聚焦能力。

```text
图例  o 待推进   o 审核中   o 待确认   o 已锁定   - 接续   = 覆盖记录

      N-001 首次推进 [锁定]
                 |
          +------+------+
          |             |
     N-002 备料      N-003 炖煮
       [锁定]          [待推进]
          |             |
          +------ N-004 收束行动 [待确认]
                         ||
                   R-002 阶段记录
```

设计要求：

- 默认展示当前节点、直接上游、直接下游和相关完成记录；复杂项目不要一次铺开整张图。
- 提供“聚焦当前路径”“查看全部”“只看锁定记录”三种视图。
- 节点点击打开右侧详情抽屉或跳转节点详情，不能仅做视觉展示。
- 图例说明颜色、实线接续、双线覆盖、分叉与多来源行动。
- 图画布的最小高度固定，缩放、平移与重置明确可见。

### 6.6 智能合约：规则库与项目历史

智能合约是项目使用的审查规则，不是节点页面上的解释性装饰。全局合约页承担批量管理，项目合约页承担选择与历史。

全局“智能合约”页面：

```text
智能合约                                            + 新建自定义合约
我的合约 | 官方推荐 | 已删除记录

合约行：名称 · 用途 · 被 N 个项目使用 · 最近使用日期   [查看正文] [更多]
```

- 正文使用 `shadcn/ui` 的 `Dialog` 或宽屏 `Sheet` 查看，不直接在列表内展开全文。
- 正文按 Markdown 渲染，保留标题、列表、引用、代码块和表格的阅读层级。
- 删除是软删除：默认列表隐藏，但“已删除记录”仍能查看名称、正文快照、删除时间和曾被哪些项目版本使用。

项目“智能合约”标签：

- 首先显示当前合约及“查看正文”。
- 其次显示本项目历次使用过的合约版本和生效区间。
- 修改只影响此后新建或新提交的审查，旧节点和旧记录永久保留其规则快照。

### 6.7 设置：少入口，明确分组

设置采用二级导航，不平铺成一张巨型表单。

```text
设置
个人资料
账号与安全
AI 密钥
智能合约
```

- `个人资料`：头像、用户名、性别、个人说明。
- `账号与安全`：邮箱、修改密码、验证码流程。
- `AI 密钥`：支持 DeepSeek、OpenAI、豆包、Claude；密钥创建后不可修改，只能测试或删除；输入时可以临时显示，保存后只显示掩码，服务端不返回原始密钥。
- `智能合约`：跳转或嵌入合约库管理。
- 项目默认使用的审查 AI 不在此设置，在每个项目的“审查 AI”标签中配置。

### 6.8 探索与公开页面：阅读其他人的执行结构

探索是独立入口，不能与“我的项目”混杂。公开页面默认只读，阅读顺序是：目标、已锁定记录、当前可接续路径、关系图摘要。

```text
探索
项目 | 阶段记录 | 执行者

公开项目
项目目标
最近锁定记录
可接续路径
关系图摘要
```

- 先用真实的阶段完成记录建立信任，再展示图谱与执行者。
- 不在第一版用点赞、排行榜或空泛热度干扰行动质量。
- 公开协作、引用与分叉必须清楚标出来源项目、原作者、采用的合约与引用关系。

### 6.9 公开协作：协作征集与成果采纳申请

公开协作不允许项目直接拿走别人的成果，也不把公共页面做成普通任务认领列表。它采用类似 GitHub Pull Request 的方向：**成果作者向目标项目主动申请采用，项目维护者决定是否纳入正式记录。**

#### 协作征集

待推进节点本身不适合在关系图中被逐一寻找。项目维护者可以为某个冻结的待推进节点发布一个独立的 `协作征集`。征集继承该节点已冻结的目标、验收标准和证据要求，不重复创建一份任务。

```text
项目节点：补足「适合初学者的火候解释」
-> 发布协作征集
-> 出现在探索页的「协作征集」与项目的「贡献」标签
-> 成果作者选择自己的完成记录，发起成果采纳申请
```

协作征集显示：项目、目标节点、验收标准摘要、当前证据缺口、审查名额、创建者、合约和审查 AI。它不是节点状态，而是绑定节点的可发现入口：

```text
征集中 | 审查名额已满 | 已关闭 | 目标节点已锁定
```

目标节点锁定时，征集自动关闭，未处理申请自动标记为“已拒绝：目标节点已锁定”。

#### 成果采纳申请

申请人只能提交自己有权限发布的、已锁定的公开阶段完成记录。一个记录可以向多个项目申请，来源记录永远保持归属、作者和原始内容不变。

```text
来源完成记录
+ 对目标节点的适配说明
+ 试图满足的验收标准
+ 尚未覆盖的缺口
-> 目标项目 AI 审查
-> 目标项目维护者确认
```

多个申请可以同时进入同一个目标节点的证据池。最终审查的对象是**全部被维护者选择纳入的成果组合**：AI 必须按目标项目的冻结合约，逐条判断这些材料整体是否满足验收标准。任何人都可以提交新的补足成果，但不能修改别人的来源记录或申请内容。

申请状态属于协作对象而不是节点：`草稿`、`已提交`、`AI 审查完成`、`请求补足`、`已采纳`、`未采纳`、`已撤回`、`目标已锁定而自动拒绝`。

#### 责任、费用与历史

- **申请人**：主动发起申请，解释成果与目标标准的关系，并可提交后续补足成果。
- **项目维护者**：开启或关闭征集、选择证据组合、确认采纳、请求补足或不采纳。
- **项目创建者**：承担该项目配置的 AI 审查费用；API Key 永远不向申请人暴露。
- **目标项目 AI**：使用目标项目当前冻结的合约和审查 AI 判断“这组外部成果是否满足本项目标准”；来源项目的 AI 只证明来源成果本身成立。

第一版协作征集有两种方式：

```text
仅邀请协作：只允许受邀执行者申请，不出现在公共征集列表。
公开征集：出现在公共列表；默认最多审查 10 份申请，同时最多保留 3 份待处理申请。
```

公开完成记录一旦被外部项目正式采用，不能删除或改为私密。作者可以归档记录、停止新的采用申请、从探索取消收录，或发布新的纠正/撤回说明记录。已被采纳的目标项目保留来源的冻结快照，并显示后续纠正提醒。这借鉴 GitHub 的公共 fork 网络对既有公开历史的处理：历史关系不能因上游后来改为私有而断裂。

#### 执行网络（基础版已实现）

探索页增加 `协作征集` 与 `执行网络`。执行网络从已锁定、已采纳的事实关系生成，不让系统把文本相似度伪装为协作。

当前基础版已经提供项目、人物、成果三个视角，并展示维护、成果形成、正在贡献、正式采纳和贡献工作区等事实关系。点击关系可以查看来源成果、项目和关系说明。

```text
当前已实现：成果形成、投稿、正式采纳、贡献工作区
后续增强：普通引用、基于成果继续、派生关系、时间回放、群落聚合
```

项目图只展示本项目的路径。全站执行网络才展示人与人、项目与项目之间的聚合关系；点击一条边必须能回到构成该关系的完成记录与采纳申请。普通引用、派生和时间回放仍属于后续增强能力。

## 7. 共享组件与状态系统

### 7.1 必须统一的组件

| 组件 | 职责 |
| --- | --- |
| `AppHeader` | 跨项目导航、搜索、新建、用户菜单 |
| `ProjectRail` | 我的项目入口、项目状态摘要 |
| `PageContextHeader` | 返回、面包屑、标题、当前主要操作 |
| `VerificationRail` | 行为 -> 验证 -> 记录的统一状态表达 |
| `NodeRow` | 队列、项目页、路径列表中的一致节点行 |
| `RecordRow` | 阶段记录的覆盖范围、AI 结论、锁定方式 |
| `EvidenceList` | 按验收标准组织的文本、链接、附件证据 |
| `ReviewResult` | 逐条审查结论、模型快照、完整原文入口 |
| `EventLedger` | 不可变事件时间线 |
| `ContractBodyDialog` | Markdown 合约正文的阅读浮层 |
| `StatusBadge` | 仅表示节点状态，不承担复杂解释 |

### 7.2 状态映射

节点只有三种主状态，界面不得创造额外的状态词替代它们：

| 主状态 | 含义 | 颜色 | 首要动作 |
| --- | --- | --- | --- |
| 待推进 | 任务已冻结，尚未提交完成材料 | `action` | 提交推进结果 |
| 待确认 AI 结果 | 审查已有结论，等待用户决定 | `review` 或 `locked/gap` 结论色 | 确认并锁定 / 新增补足 |
| 已锁定 | 已进入阶段完成记录或被记录覆盖 | `locked` | 查看记录 |

“AI 审核中”是过程态，不是第四种节点主状态。它出现在待推进与待确认之间，以验证轨或队列标签表现。AI 审查通过/未通过是审查结论，不等于节点主状态。

### 7.3 数据表达优化

为了让前端不靠拼文案解释复杂关系，后端和前端数据模型应能直接表达：

- `node.taskReview` 与 `node.completionReview`：分别保存创建审查、完成审查及模型配置快照。
- `completionRecord.coveredNodeIds`：明确记录覆盖的节点集合。
- `node.parentIds`：支持一个普通行动节点引用多个前置来源。
- `eventLog`：创建、冻结、提交证据、发起审查、审查返回、确认锁定、未通过锁定、创建补足等不可变事件。
- `project.contractRevisionId` 和 `project.reviewAIKeyId`：只保存当前默认值；节点与记录保存实际使用的快照。
- `collaborationCall`：项目维护者为一个待推进节点发布的协作征集，保存开放方式、审查总额度、同时待处理额度与关闭原因。
- `recordAdoptionRequest`：成果作者主动向目标节点提交的采纳申请，保存来源完成记录、拟满足的目标标准、适配说明、目标 AI 审查、维护者决定与来源快照。
- `recordRelation`：长期模型中只在锁定或正式采纳后生成的事实边，类型包括引用、采用、派生、共同收束；来源和目标可以跨项目。当前实现已提供成果形成、投稿、正式采纳等关系，普通引用、派生和共同收束仍待独立操作与事实模型支持。
- `networkEdge`：由 `recordRelation` 聚合出的只读查询结果。项目网络按项目聚合，执行者网络按作者/维护者聚合；任何边都必须能展开为具体记录与申请，不能只存一个不可解释的相似度分数。

## 8. 核心流程

### 8.1 第一次使用

第一次登录后不要求用户先理解图谱、合约版本或公共探索。根页面只提供一个清晰的入口：`新建项目`。

```text
新建项目
1. 填项目名称与一句目标
2. 选择智能合约
3. 选择项目审查 AI
4. 创建项目
5. 在项目内创建第一项推进
6. AI 审查任务描述，用户确认后开始推进
```

创建项目时不强制填写第一个任务。首个任务和普通任务一样，在项目内单独创建，并接受“任务描述审核”。这样项目的存在与第一项行动不会被混成一个对象。

### 8.2 日常推进

```text
工作总览发现待推进
-> 打开节点“任务完成”
-> 按验收标准提交证据
-> AI 完成审查
-> 用户确认并锁定，或新增补足节点/带未通过结论锁定
-> 记录生成，下一项可从当前路径继续或分叉
```

“新增补足节点”需要提供两种默认预设：

- **继续此节点**：新节点接续当前未闭合的工作。
- **拆出遗漏工作**：新节点引用当前节点，形成独立补足路径。

用户不需要先理解“分叉”术语；结构由来源关系自然形成，图谱中才明确表现为分叉。

### 8.3 多路径收束

收束不是单独的“合并”功能。用户新建一个正常行动节点，选择多个前置来源；当它提交的证据通过审查并被确认后，系统生成覆盖这些来源的阶段完成记录。

界面必须明确：

```text
本次锁定将覆盖：N-010、N-011、N-014
这是一次阶段完成记录，不会修改各节点的原始行动内容。
```

## 9. 功能优先级

### P0：保证核心闭环可用

1. 工作总览以“等待确认 -> 审核中 -> 待推进”排序，所有条目可直达处理位置。
2. 节点详情具备任务、完成、事件三个清楚标签，创建审查与完成审查独立展示。
3. 完成证据按验收标准组织；AI 结论可逐条映射到标准。
4. 用户确认锁定、AI 未通过后锁定、创建补足节点三个路径完整可用。
5. 项目记录展示节点覆盖关系、合约/AI 快照、用户最终决定。
6. 项目内独立的节点、记录、关系图标签，关系图支持聚焦当前路径。
7. 项目选择审查 AI；每次审查永久记录实际使用的密钥标签、服务商与模型名称。
8. 合约正文通过 Markdown 浮层查看；项目能查看当前合约与历史合约。

### P1：增强理解与可追溯性

1. 全局搜索：项目、节点、完成记录、公开项目。
2. 站内通知：AI 审查返回时生成可直接跳转的通知。
3. 证据附件与预览：链接、图片、文件、文本片段。
4. 记录与图谱筛选：路径、时间、审查结论、覆盖范围。
5. 项目只读归档与项目历史导出（归档恢复已实现，历史导出仍待实现）。

### P2：传播与公共网络（基础版已交付，后续能力仍在规划）

1. 协作征集、成果采纳申请、证据池与维护者确认（基础版已实现）。
2. 公开项目的普通引用、基于成果继续和派生来源链（待实现；当前已有节点来源和协作采纳关系）。
3. 执行者与路径的发现、关注、订阅更新。
4. 基于被接续、被覆盖、近期有效推进的质量信号，而非简单点赞的排序。
5. 完成记录网络、跨项目目标场与执行关系图谱（基础网络已实现，多尺度聚类和时间回放待实现）。

## 10. 实施迁移

### 阶段一：骨架与视觉令牌

- 将全局画布从暖纸张网格改为冷灰绿 `canvas`，更新 Tailwind 颜色令牌。
- 重写 `AppShell`：固定顶栏、固定左栏、主内容固定上下文头。
- 将顶栏导航确定为工作总览、探索、搜索、新建项目、用户菜单。
- 规范 `PageContextHeader`、按钮、标签、状态徽标和 Toast。

验收：任意页面在常用桌面宽度下没有文字溢出、重叠或无意义的大空白；侧栏不随主内容滚动；主内容页头保持可见。

### 阶段二：核心行动闭环

- 重构 `DashboardPage` 为决策队列，去除非决策型仪表盘占位。
- 重构 `ProjectPage` 默认工作台，将记录抽为独立标签。
- 重构 `NodePage`：`任务描述 / 任务完成 / 事件`，引入验证轨与结构化审查结论。
- 接入 `NodeRow`、`RecordRow`、`ReviewResult`、`EventLedger` 的共享组件。

验收：用户可从根路径在两次点击内到达任何待处理节点；能看出审查正在何处发生、结果是什么、自己接下来可做什么。

### 阶段三：关系、规则与配置

- 将 `ProjectGraph` 迁入独立标签，增加图例与聚焦视图。
- 统一智能合约库、项目当前合约、合约历史与 Markdown 正文 Dialog。
- 收束项目审查 AI 与账号密钥的职责边界。

验收：用户能在不阅读帮助文的情况下，从项目找到当前合约和 AI；从任一完成记录找到覆盖节点、审查结论与规则快照。

### 阶段四：探索与通知

- 统一公开项目、公开执行者与探索页的阅读型布局。
- 加入 AI 审查结果通知和跨项目搜索。
- 以真实完成记录驱动发现排序，避免先做泛社交流。

验收：公共阅读页没有写操作混入；收到审查结果的用户能直接到准确节点与标签页处理。

## 11. 页面验收清单

### 全局

- [ ] 顶栏与侧栏的职责不重叠；“我的项目”是左栏唯一核心内容。
- [ ] 所有状态颜色有一致语义，不用颜色装饰页面。
- [ ] 主要操作使用明确动词；图标按钮有 Tooltip 与可访问名称。
- [ ] Toast 在页面顶端出现并自动消失，成功、失败、审核返回文本一致。
- [ ] 键盘焦点清楚，弹窗能正确聚焦和关闭。

### 工作总览

- [ ] 首屏首先显示“等待你的确认”。
- [ ] 每个待处理项显示项目、节点、状态与一个明确动作。
- [ ] 空状态告诉用户下一步，例如“新建项目”或“创建第一项推进”。

## 12. 方案自检

本方案主动避开三种容易落入模板的选择：

1. **暖奶油纸张 + 大衬线标题 + 陶土色强调**：当前页面已有这种倾向，且更像笔记产品。改用灰绿档案底色与语义状态色，视觉来自“事实记录”而非通用生产力审美。
2. **黑底 + 荧光色的伪命令行感**：`>_` Logo 保留终端提示的克制暗示，但整体依旧是高可读性浅色工作界面，避免把工具做成开发者海报。
3. **满屏大卡片仪表板**：产品不是汇报指标，而是处理下一次行动。队列、验证轨、记录行和关系图各自承担具体信息任务，避免卡片嵌套。

这个方向的风险是信息密度过高。控制方式是：日常页面只呈现“当前行动”和最近记录；完整关系、长正文、历史版本全部放进标签、筛选、抽屉和浮层中，需要时再展开。
